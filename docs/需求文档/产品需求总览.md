# AI 评测迭代工作台产品需求总览

## 1. 产品背景

AI 客服每天产生大量对话，人工抽检覆盖率低，而且“不好”往往无法直接解释为知识缺失、理解错误、流程错误或服务态度问题，导致抽检结果难以转化为具体改进动作。

本产品通过自动评测、问题归因、QA 审核、发布复测和人工校准，建立一条可执行、可追溯的 AI 质量改进闭环。

## 2. 目标用户

- AI 产品经理。
- 客服运营和质检负责人。
- 知识库运营团队。
- 负责 AI 产品质量的单人或小型团队。

## 3. 产品目标

1. 扩大对话质量评测覆盖面，减少对纯人工抽检的依赖。
2. 为每条评测提供分数、理由、证据和版本信息。
3. 把不合格案例转化为明确的问题原因和改进任务。
4. 对知识缺失生成可人工审核、可导出的 QA。
5. 通过历史回放和发布后新样本验证改进是否有效。
6. 通过人工校准持续检查模型评测是否可信。

## 4. 产品约束

- 单人维护、单台服务器部署。
- 日处理量低于 10,000 条对话。
- 首版使用 MySQL，不引入复杂消息中间件。
- 大模型只提供建议，不自动确认归因、批准 QA 或发布知识。
- API Key 只保存在后端配置中。
- 对话进入模型前必须脱敏。

## 5. 功能模块

| 编号 | 模块 | 核心职责 |
| --- | --- | --- |
| 01 | [今日工作台](./01-今日工作台.md) | 汇总质量状态、待办和优先任务 |
| 02 | [问题与归因](./02-问题与归因.md) | 聚合失败案例，AI 建议原因并由人工确认 |
| 03 | [QA 审核](./03-QA审核.md) | 生成、编辑、审核和导出知识库 QA |
| 04 | [发布与复测](./04-发布与复测.md) | 登记改进发布并验证效果是否恢复 |
| 05 | [数据采集](./05-数据采集.md) | 上传 JSON、映射字段、脱敏预览和入库 |
| 06 | [发起评测](./06-发起评测.md) | 抽样对话并调用真实模型完成质量评测 |
| 07 | [评测规则](./07-评测规则.md) | 管理公司质量标准和评测 Prompt 版本 |
| 08 | [评测校准](./08-评测校准.md) | 人工复核模型判定并沉淀回归案例 |

## 6. 核心业务流程

```text
配置公司标准与评测 Prompt
-> 上传并确认对话数据
-> 发起真实评测
-> 聚类不合格案例
-> AI 建议归因，人工确认原因
-> 生成并审核 QA 或创建其他改进任务
-> 外部发布后登记
-> 历史回放与新增样本复测
-> 达标后关闭问题，未达标则继续改进
-> 人工校准评测结果并沉淀回归案例
```

## 7. 通用业务规则

- 历史评测必须锁定当时的数据、公司标准、Prompt 和模型版本。
- 新版本不能覆盖历史结果。
- AI 生成内容必须经过结构校验，重要决策必须人工确认。
- 重复上传、重复点击和任务恢复不能造成重复数据或重复计费。
- 页面必须区分真实数据、演示数据、待处理状态和最终结果。
- 所有人工确认、版本发布、QA 审核和复测结论应保留审计记录。

## 8. MVP 不包含

- 多租户、复杂角色权限和多人抢单。
- 自动接入所有第三方客服平台。
- AI 自动发布 QA 或自动修改评测规则。
- 直接写入企业知识库。
- 微服务、Kafka、Redis 或独立工作流引擎。
- 全自动 Prompt 优化和跨版本实验平台。

## 9. 总体验收标准

1. 用户可以从 JSON 数据完成一次真实评测。
2. 不合格案例可以进入归因并创建对应改进任务。
3. 知识缺失可以生成、审核并导出 QA。
4. 已发布改进可以通过双样本复测得到明确结论。
5. 每条结论都可以追溯到对话证据及当时使用的规则版本。
6. 单条模型调用失败不会中断整个批次。
7. 单台服务器可以稳定支持首版目标处理量。
