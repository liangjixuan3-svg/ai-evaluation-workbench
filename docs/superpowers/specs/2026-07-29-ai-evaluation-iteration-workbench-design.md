# AI 评测迭代工作台设计规格

## 1. 文档信息

- 日期：2026-07-29
- 状态：已完成产品设计对齐，待用户审阅书面规格
- 产品名称：AI 评测迭代工作台
- 目标用户：负责 AI 产品质量的产品经理、运营负责人及客服质量团队
- 首期示例场景：电商客服中的退款进度查询、物流异常催单

## 2. 背景与问题

AI 客服上线后每天会产生数千条对话，人工抽检每天只能覆盖约一百条，覆盖率通常低于 2%。现有抽检即使发现回答“不好”，也往往无法进一步说明问题来自知识库缺失、AI 理解错误、业务流程执行错误还是服务态度不佳。不同原因需要不同修复方式，导致抽检结果难以直接转化为行动。

本产品需要把质量运营从零散抽检升级为可追踪的闭环：自动抽取线上对话，通过大模型逐条评测并提供证据；质量异常时生成告警；对不合格案例聚类并分析原因；对知识缺失自动生成有依据的 QA 草稿；经人工审核和发布后复测，确认质量是否恢复。

## 3. 目标与非目标

### 3.1 产品目标

1. 让运营人员在 30 秒内判断今天是否存在质量异常、应该先处理什么以及处理进度。
2. 每个质量结论都能追溯到原始对话、扣分证据、模型版本、Prompt 版本和规则版本。
3. 将不合格案例从“现象”转成明确的原因分类与后续修复任务。
4. 对知识缺失生成可审核、可编辑、可导出的 QA 草稿。
5. 修复后通过历史回放和新增线上样本验证效果，形成可审计闭环。
6. 在单人维护、单台服务器、日对话量低于 1 万条的条件下稳定运行。

### 3.2 非目标

首版不建设微服务、Kafka、独立工作流引擎或复杂多租户体系；不直接写入外部知识库；不允许 AI 自动发布 QA；不追求全量对话都调用大模型；不把数据采集配置作为产品主入口。

## 4. 产品原则

### 4.1 任务驱动，而非图表驱动

主入口为任务工作台。看板负责观察和分析，流水线页面负责运行和排障，任务工作台负责推动告警、归因、修复和复测。看板指标或流水线结果只有转成明确任务后，才算进入质量运营流程。

### 4.2 分开描述问题与解释原因

质量维度回答“哪里答得不好”，例如正确性、完整性或相关性；根因分类回答“为什么不好”，例如知识缺失或理解错误。两类结果分别建模，避免用同一个标签同时承担评分和修复决策。

### 4.3 人工负责高风险决策

AI 可以评测、聚类、建议归因和生成 QA 草稿，但归因确认、QA 批准、外部发布状态和误报告警关闭均由人工完成。缺乏业务依据的 QA 草稿不得批准。

### 4.4 闭环终点是效果恢复

告警不会因为被查看、完成归因或导出 QA 而关闭。修复发布后必须复测；达到恢复阈值才能关闭，否则重新进入待处理状态。

## 5. 信息架构

左侧一级导航保留六项：

1. 任务工作台：今日质量状态、优先告警、个人待办和最近动态。
2. 质量看板：质量趋势、场景分布、问题类型与修复效果分析。
3. 评测管理：数据源、采样规则、评测模板、Prompt 版本和运行记录。
4. Badcase 中心：不合格案例检索、聚类、归因确认和人工反馈。
5. 改进产物：QA 草稿、其他优化任务、导出记录和复测任务。
6. 系统配置：模型、告警规则、脱敏规则和基础字典。

数据采集、Prompt 模板和预警规则不再各占一个一级入口，避免导航过碎。

## 6. 核心页面与交互

### 6.1 任务工作台首页

首页按以下顺序呈现：

1. 顶部质量状态：整体通过率及变化、新增告警、待确认归因、待审核 QA。
2. 优先处理：按 P1、P2、P3 展示告警，优先级相同时按影响范围和持续时间排序。
3. 我的待办：待确认归因、待审核 QA、待复测修复。
4. 最近动态：评测完成、告警产生、归因确认、QA 导出和复测结果。
5. 最近评测：仅作为运行记录，不抢占主视线。

每张任务卡必须提供严重程度、影响范围、与正常基线的差异、代表性失败原因、当前处理状态和唯一明确的下一步操作。首页提供“发起评测”，但不把流水线运行状态作为视觉中心。

### 6.2 告警详情与归因

告警详情遵循“异常证据 -> AI 归因建议 -> 人工确认 -> 后续修复任务”的主线，包括：

- 异常概况：当前指标、正常基线、影响数量、持续时间和主要集中场景。
- AI 归因汇总：各原因数量、置信度分布和代表性问题簇。
- 代表性样本：对话原文、评分、扣分理由、AI 建议归因及置信度。
- 操作区：确认归因并生成修复任务、标记误报、暂缓处理。

系统先对相似 badcase 聚类，每个问题簇默认展示 2 至 3 条代表样本。高置信度结果允许批量确认，中低置信度结果要求人工查看。运营人员可修改单条归因，所有修改作为评测校准反馈保存。

归因确认后按类型分流：

- 知识缺失：生成 QA 草稿审核任务。
- 理解错误：生成 Prompt 或意图识别优化任务。
- 流程执行错误：生成接口、工具调用或业务流程排查任务。
- 服务态度：生成话术规范优化任务。
- 评测误报/其他：记录人工反馈，用于校准评测规则。

告警状态为：`待处理 -> 分析中 -> 待修复 -> 待复测 -> 已恢复/未恢复`。标记误报需要填写简短原因并保留审计记录。

### 6.3 QA 草稿审核

QA 草稿至少包含：关联 badcase 数量、代表对话、参考业务资料、生成置信度、建议问法、建议答案、适用条件、处理步骤、预计时效和升级人工条件。

审核操作包括批准、编辑后批准、驳回和退回重新生成。约束如下：

- 无可引用业务资料时标记“缺少依据”，禁止批准。
- 仅批准后的版本可以导出。
- 保存来源 badcase、审核人、修改记录、版本和导出记录。
- 首版支持 CSV 和 JSON 导出，由知识库团队导入后人工回填“已发布”。

### 6.4 复测闭环

知识或其他修复项标记发布后，系统建立复测任务并使用两组样本：

- 回放样本：原告警中的失败案例，验证已知问题能否被修复。
- 新增样本：发布后的同类线上对话，验证真实效果并避免只适配历史案例。

复测展示修复前后通过率、各质量维度变化、仍失败案例和新的主要原因。达到规则配置的恢复阈值后告警进入“已恢复”；未达到则进入“未恢复”，重新生成待处理任务。

## 7. 评测体系

### 7.1 质量维度

首版提供五个通用维度，具体权重和通过阈值由评测模板配置：

1. 正确性：事实、政策、业务结论和承诺是否正确。
2. 完整性：是否覆盖用户完成任务所需的关键信息。
3. 相关性：是否理解问题并直接回应。
4. 服务体验：表达是否清晰、耐心且不过度机械。
5. 合规性：是否涉及越权承诺、隐私、安全或其他合规风险。

输出包括总分、各维度分、通过/不通过、具体理由、引用证据和置信度。严重事实错误或严重合规问题属于一票否决，不能被其他维度高分抵消。

### 7.2 根因分类

只有不合格案例进入根因阶段。首版分类固定为知识缺失、理解错误、流程执行错误、服务态度、评测误报/其他。根因输出必须包含理由、对话证据和置信度。

### 7.3 版本与可追溯性

每条评测保存模型供应商、模型标识、模型参数、Prompt 版本、评测模板版本、规则版本和执行时间。历史结果不可被新版本覆盖；重新评测生成新记录，并可对比差异。

### 7.4 黄金数据集

维护一批经过人工标注的代表性对话，覆盖正常案例、各类 badcase、边界情况及一票否决情况。模型、Prompt 或评测规则变更前运行回归，结果低于允许偏差时禁止直接设为默认版本。

## 8. 抽样与告警

### 8.1 抽样策略

每日样本由三部分组成：

- 基础随机样本：用于观察整体质量，避免只关注已知问题。
- 重点场景加权：提高退款、投诉、物流异常等高风险场景覆盖率。
- 风险规则命中：命中特定词、用户重复追问、转人工、负反馈等规则时优先进入评测。

采样规则配置每日预算和各部分比例。复测样本独立管理，不占普通抽样预算。采集使用外部对话 ID 去重。

### 8.2 告警策略

系统同时支持三类告警，但优先级不同：

1. 主触发器：某类问题数量或失败率相对基线显著激增。
2. 辅助触发器：重点业务场景通过率或关键维度异常。
3. 兜底触发器：整体总分或通过率持续下降。

单点波动默认不立即告警。规则结合最低样本量、变化幅度和持续窗口，减少小样本噪声。相同场景、相同问题类型在时间窗口内合并为同一告警，并更新影响范围。

## 9. 数据流

完整数据流为：

```text
线上对话
-> 接入与标准化
-> 脱敏和去重
-> 规则抽样与重点场景加权
-> LLM 质量评测
-> 不合格案例聚类
-> LLM 根因分析
-> 告警与人工确认
-> QA 或其他修复任务
-> 人工审核和发布回填
-> 历史回放与新增样本复测
-> 恢复或重新进入待处理
```

各阶段保存独立状态和输入输出摘要，支持从失败阶段恢复，并能追溯一条原始对话最终产生了哪些告警、修复项和复测结果。

## 10. 技术架构

### 10.1 架构选择

采用模块化单体，单台服务器使用三个容器部署：

- Web/API：React 管理界面和 FastAPI 业务接口。
- Worker：定时采集、批量评测、聚类、归因和复测任务。
- PostgreSQL：业务数据、审计数据和数据库任务队列。

首版不引入 Redis、Kafka 或独立工作流引擎。前端构建后由 Web 容器提供静态资源。模块通过明确的应用服务接口协作，共享数据库但不跨模块直接修改对方状态。

### 10.2 业务模块

- 数据接入：连接外部数据源，将对话转换为统一结构。
- 抽样评测：执行抽样、调用模型并验证结构化结果。
- Badcase 分析：聚类不合格案例并生成根因建议。
- 告警任务：计算告警、管理优先级和状态流转。
- 改进产物：生成、审核、版本化和导出 QA 及其他修复任务。
- 复测看板：组织复测样本，计算修复效果和趋势指标。
- 模型适配：封装模型调用、重试、限流、成本与用量记录。

### 10.3 核心数据实体

核心实体包括数据源、原始对话、标准化对话、采样批次、评测模板、Prompt 版本、评测运行、单条评测结果、Badcase 问题簇、根因建议、告警、任务、QA 草稿及版本、导出记录、复测运行、模型调用记录和审计日志。

对话正文与评测结果分开保存；任务引用结果，不复制正文。状态变更通过领域服务执行并写入审计日志。

## 11. 异常处理与安全

- 每个阶段独立记录状态，失败后从当前阶段重试，不重跑完整流水线。
- LLM 超时、限流和临时错误采用指数退避；超过上限后进入待人工处理。
- 单条失败不阻断批次，批次报告成功数、失败数和失败原因。
- 模型返回内容必须通过结构校验，无法修复的输出不进入正式评测结果。
- 使用外部对话 ID 和数据源 ID 组成幂等键，避免重复采集和重复计费。
- 对话发送给模型前按规则脱敏手机号、地址、订单标识等敏感信息。
- API 密钥只从环境变量读取，不存入数据库或前端。
- QA 缺少可引用业务依据时禁止批准；任何发布状态均由人工回填。
- 系统记录人工修改、状态变化、导出和重试，提供审计查询。

## 12. 测试策略

### 12.1 单元测试

覆盖抽样规则、评分计算、一票否决、告警阈值、告警合并、状态流转、幂等去重和 QA 审批约束。

### 12.2 合约测试

使用模型响应样例验证各模型适配器均可转换为统一结构，并覆盖缺字段、类型错误、截断和非 JSON 响应。

### 12.3 黄金数据集回归

对模型、Prompt 和模板版本变更执行固定数据集回归，比较通过率、维度分、根因分类和人工标注一致率。

### 12.4 集成与端到端测试

集成测试覆盖数据库事务、任务领取、失败重试和批次部分成功。端到端测试使用模拟数据和模拟模型，跑通采集、评测、告警、归因确认、QA 审核导出、发布回填、复测和告警关闭。

## 13. 可观测性与运维

系统提供任务运行记录、阶段耗时、成功/失败数量、重试次数、模型调用量和估算成本。保留结构化日志并关联运行 ID、批次 ID 和对话 ID。后台任务卡死时可由管理页重新入队；数据库按日备份，并验证恢复流程。

## 14. 首版验收标准

1. 可使用模拟数据跑通完整闭环，且后续能通过统一接入接口替换为线上数据源。
2. 运营人员能从首页进入告警，在问题簇层面查看证据、确认或修改归因。
3. 每个分数、扣分理由和根因可追溯到对话证据及对应版本。
4. 确认知识缺失后可生成有业务依据的 QA 草稿，人工批准后导出 CSV 或 JSON。
5. 修复发布后可同时执行历史回放和新增线上样本复测，并展示前后对比。
6. 告警只有复测达到恢复阈值或被人工标记误报时才能关闭。
7. 单条模型调用失败不会导致整个批次失败，且可从失败阶段恢复。
8. 同一对话重复接入不会产生重复评测费用或重复告警。
9. 日处理量低于 1 万条时，系统可在单台服务器稳定执行计划任务和人工操作。

## 15. 实施边界与顺序

实现时按一条可演示纵向闭环推进，而不是先分别完成所有页面：模拟数据接入 -> 基础评测 -> 告警任务 -> 归因确认 -> QA 草稿审核与导出 -> 发布回填 -> 复测。完成纵向闭环后再补充看板分析、模板管理和高级筛选。

本规格覆盖首版完整产品闭环，后续直接对接不同客服平台、自动写入知识库、多租户、复杂权限和模型自动优化均作为独立迭代，不纳入首版。
