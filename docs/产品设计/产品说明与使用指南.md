# AI 评测迭代工作台：产品说明与使用指南

## 1. 产品是什么

AI 评测迭代工作台是一套面向 AI 产品经理、运营负责人和客服质量团队的质量闭环工具。它把线上对话从“抽样查看”推进到“自动评测、明确原因、生成改进内容、人工审核、发布复测和评测校准”。

典型场景是电商 AI 客服：每天产生数千条退款、物流、售后对话，人工只能抽检很小一部分。工作台利用大模型扩大评测覆盖面，同时保留人工对归因、QA 发布和评测正确性的最终决定权。

## 2. 解决什么问题

传统人工抽检常停留在“这条回答不好”，无法直接回答：

- 是知识库缺少信息，还是模型理解错了？
- 是业务流程没有执行，还是服务态度不合格？
- 应该补知识、改 Prompt、修接口，还是调整评测规则？
- 改完以后，线上质量是否真的恢复？

本产品把“质量现象”和“问题原因”分开处理，并让每种原因进入不同的改进路径。

## 3. 产品原则

1. **任务驱动**：首页告诉用户下一步做什么，而不是只展示图表。
2. **结论可追溯**：评分关联原对话、证据、公司标准、Prompt 和模型版本。
3. **人机分工明确**：AI 负责评测、建议归因和生成草稿；人工负责确认、批准和发布。
4. **闭环以复测为终点**：发现问题或发布 QA 都不算完成，只有复测恢复才闭环。
5. **轻量可维护**：单人维护、单台服务器、日处理量低于 10,000 条，不引入不必要的复杂基础设施。

## 4. 页面模块

| 编号 | 模块 | 主要作用 | 什么时候使用 |
| --- | --- | --- | --- |
| 01 | 今日工作台 | 汇总质量状态和优先待办 | 每天开始质量运营时 |
| 02 | 问题与归因 | 查看失败问题簇、生成 AI 建议并人工确认原因 | 一次评测出现不合格案例后 |
| 03 | QA 审核 | 生成、编辑、审核和导出知识缺失 QA | 归因确认为知识缺失后 |
| 04 | 发布与复测 | 登记外部发布，使用历史与新增样本验证效果 | QA 进入知识库或其他改进上线后 |
| 05 | 数据采集 | 上传 JSON、映射字段、脱敏预览并确认入库 | 有一批新的客服对话时 |
| 06 | 发起评测 | 选择数据和规则，调用模型并查看逐条结果 | 数据入库且规则准备完成后 |
| 07 | 评测规则 | 管理公司质量标准、评测 Prompt 和历史版本 | 首次使用或质量标准变更时 |
| 08 | 评测校准 | 人工复核模型判定，沉淀分歧和回归案例 | 有正式评测结果后持续进行 |

## 5. 完整业务闭环

```text
配置评测规则
-> 上传并确认对话数据
-> 发起真实模型评测
-> 聚类不合格案例
-> AI 建议原因，人工确认归因
-> 知识缺失生成 QA 草稿
-> 人工审核并交付知识库团队
-> 登记发布并复测
-> 达标后确认恢复；未达标重新进入改进
-> 人工校准模型评测，形成回归案例
```

## 6. 第一次使用

### 6.1 启动系统

按照项目根目录的[使用说明](../../使用说明.md)准备 MySQL、后端虚拟环境、模型配置和前端依赖。每次使用需要手动启动：

1. 后端 API。
2. 评测 Worker。
3. 前端网页。

网页地址为 `http://127.0.0.1:5173`。

### 6.2 配置评测规则

先进入“07 评测规则”：

1. 上传公司的 Word 或文本型 PDF 制度文档；体验功能时可使用 [`示例数据/公司客服质量标准示例.docx`](../../示例数据/公司客服质量标准示例.docx)，示例内容不得直接用于真实业务。
2. 让 AI 提取评分规则，人工核对阈值、五维权重、评分说明和原文引用。
3. 所有规则确认后发布公司标准；发布版本锁定，历史评测始终可追溯。
4. 在“评测 Prompt”中检查内置版本；需要调整时复制为新草稿，修改后发布。

公司标准决定“具体评什么”，Prompt 决定“模型怎样执行判断和解释”。两者都必须发布后才能用于真实评测。

### 6.3 导入数据并发起评测

1. 进入“05 数据采集”上传 JSON。
2. 确认记录数组、对话 ID、时间、场景和消息字段。
3. 检查脱敏预览并确认入库。
4. 进入“06 发起评测”，选择刚才的数据批次、抽样策略、公司标准和 Prompt。
5. 启动后在运行页查看完成进度、通过率、维度分、理由和证据。

## 7. 日常问题处理

### 7.1 从首页开始

打开“01 今日工作台”，优先处理队列已经按优先级和影响范围排序。点击卡片进入问题归因、QA 审核或复测，不需要自己在多个列表中寻找下一步。

### 7.2 确认问题原因

在“02 问题与归因”查看问题簇和代表对话。需要时生成一次 AI 归因建议，再由人工选择最终原因并填写依据：

- 知识缺失：进入 QA 审核。
- 理解错误：形成 Prompt 或意图识别优化任务。
- 流程执行错误：排查接口、工具调用或业务流程。
- 服务态度：调整话术规范。
- 评测误报/其他：作为评测校准反馈。

### 7.3 审核 QA

在“03 QA 审核”生成 QA 草稿，核对问题、答案、适用范围、处理步骤、时效和升级条件。必须填写可引用的业务依据，才能审核通过并导出 JSON 或 CSV。系统不会自动把 QA 写入外部知识库。

### 7.4 发布与复测

知识库团队完成发布后，在“04 发布与复测”登记操作人和备注。系统准备两组样本：原失败案例的历史回放，以及发布后的同场景新对话。两组都达到阈值才判定改善有效，否则继续改进。

## 8. 评测校准

“08 评测校准”每天从正式评测中准备最多 20 条高价值案例，包括低置信度、阈值边界、严重错误和随机样本。人工可以认同模型判定，也可以给出正确结论、主要分歧维度和业务依据。

校准过程不调用模型、不消耗 Token，也不会覆盖原始评测结果。不认同案例会进入回归集合，用于后续检查公司标准、Prompt 或模型变更是否改善了评测一致性。

## 9. 版本与责任边界

- **公司质量标准**：定义阈值、权重、评分说明和业务规则。
- **评测 Prompt**：约束模型的判断步骤、解释方式和输出要求。
- **模型**：根据锁定的标准和 Prompt 输出评分、理由、证据与置信度。
- **人工审核人**：确认归因、QA 内容、发布状态和校准结论。
- **Worker**：异步执行真实评测；关闭后新任务会等待，不会丢失已完成结果。

每次评测和复测都锁定当时使用的标准、Prompt、模型和数据范围。新版本不会改写历史结果。
